# Phase 0, steps 1 to 6 — Launch

Part of `/spec-audit:start`, whose folder is `skills/start/` of the plugin (`SKILL.md` gives its full path as `${CLAUDE_SKILL_DIR}`, which a file read afterwards does not substitute: below, `${CLAUDE_SKILL_DIR}` means that folder), which it continues: read by the launcher, or by the orchestrator with `--in-session`, before step 7. The section numbers and the terms (register, oracle table, worktree, audit session) are those of `SKILL.md`; the register format is in `references/register.md`.

**Architecture, first.** Check the project's architecture before anything is asked, created or spent (`SKILL.md`, "Project architecture"): `python3 ${CLAUDE_SKILL_DIR}/references/arch.py require --root "<repository root>"` (`python` where `python3` does not print a Python 3 version). Without `SPECAUDIT_ARCH.md` (exit 2), say that the project has no architecture yet, that `/spec-audit:init` proposes it and writes it once confirmed, and stop: no account question, no worktree, no index entry, no question at all, in every mode. With an invalid one (exit 1), stop the same way with its errors. Then check that every document of `<document>` is `audited` (`arch.py role --root … <paths>`); one that is not stops the audit the same way, naming its role. Keep the output: step 5 records it.

**Account, before anything else.** Unless `--in-session` is given, the audit runs in a `claude -p` session (step 6), billed to the account the claude CLI is logged into, which need not be the account of your session: a project may point it elsewhere (`CLAUDE_CONFIG_DIR` in its settings), and the CLI's default login may change. An audit costs several agents per pass, so the account is settled before anything is created or spent. `<python> ${CLAUDE_SKILL_DIR}/references/account.py list` gives, for each configuration folder (`~/.claude`, the default, and every `~/.claude-*`), its account (`email`, `org`), whether it is logged in, and which one the CLI uses here (`current`).
   - `--account <email>` given: the current folder's account must be that e-mail, or else another logged-in folder's, which is then used for this audit only; if none is, stop and say which accounts were found.
   - Otherwise ask, with AskUserQuestion (header "Account"), about the current folder: **Continue with <email> (<organization>)**; **Use another account**; **Run in this session**, which continues as with `--in-session`, on this session's account. No option is recommended: the account is the user's choice. If the current folder is not logged in, ask the same question without the first option.
   - **Continue**: if the project's `.claude/settings.local.json` does not set `CLAUDE_CONFIG_DIR` yet, ask once more (header "Remember"): **Remember it for this project**, which runs `account.py remember "<project root>" "<folder>"`, so that the project keeps this account even if the CLI's default login changes; or **This audit only**.
   - **Use another account**: ask which (header "Account"), one option per other logged-in folder, with its e-mail, and **An account not logged in yet**, which stops the audit with the command to run, `CLAUDE_CONFIG_DIR="$HOME/.claude-<name>" claude auth login`, then to launch again. Never log in or out yourself: `claude auth logout` would disconnect that folder for every project and session that uses it, and logging in is the user's act. Then ask "Remember" as above.
   - When no question can be asked (a non-interactive session), go on only with a matching `--account`; without it, stop before step 1, saying the account found and the option to pass: nothing must be spent on an account nobody confirmed.

   The folder chosen is passed to the audit session explicitly (step 6), since this session does not reread its settings: a folder remembered now applies to the sessions started afterwards. The folder alone does not decide the account: a session started by another (the Claude desktop app, an Agent SDK host, a `claude` session) hands its children its own credentials, a local proxy or a token, which win over `CLAUDE_CONFIG_DIR`, so that `claude auth status` names the folder's account while every request is billed to the parent's. `account.py clean-env` lists those variables as `-u <name>` arguments of `env` (nothing when there are none): the audit session is always launched under `env <clean-env>` (step 6), and `account.py list` reads the folders the same way. Record the account, its folder and how it was settled (question, `--account`, remembered or not) in the register at step 5.

1. **Project rules.** Read `CLAUDE.md`, the project's conventions and memory: they take precedence over this skill (attribution headers, document versioning, push policy, scope of the theory, status of proofs). Read the architecture (`arch.py show --root … --config <configuration> --json`): the profile of each audited document and its normative dependencies (`arch.py normative`) come from it. Read the project configuration (`.specaudit.md` or `.specaudit/config.md`, see "Project configuration"), if there is one: its version convention and defaults apply to this audit, and its notes guide you; its keys `profiles` and `normative`, if present, are deprecated: apply them where the architecture says nothing, say once that they moved to `SPECAUDIT_ARCH.md` (`/spec-audit:init` moves them), and record it (step 5). A document whose profile does not exist yet: say so, and ask whether to audit it with `formal` or to stop.
2. **Version convention.** Does the project fix the document in place, or create a new revision (new file, history section)? Follow the convention; if it is unclear, ask once.
3. **Dedicated branch and worktree.** Unless `--no-worktree` is given, the whole audit runs on a branch of its own, checked out in a git worktree created for it: the document is modified there, the corpus grows there, the commits stay there, without touching the user's directory or the sessions working in it in parallel. The audit never merges that branch (phase 8): it ends with a final commit on it, and the user merges it, or not, by their own means.
   - `<slug>`: the document name without extension, or the folder name for a folder, in lowercase ASCII, words separated by hyphens.
   - Record the path of the original repository, its current branch and its head commit, and note them in the register: closing (phase 8) depends on them.
   - Record `git status` of the current repository. If the document, its normative dependencies or the corpus have uncommitted changes, they will not exist in the worktree: ask the user whether to audit the committed version or to commit first. Do not use `git stash`, which is shared between all worktrees.
   - **Session history.** Tools that record your sessions keep their history inside the project: `.forge/` (tokenforge's snapshots and handoffs), or any similar folder of transcripts, session notes or handoffs. A reviewer who lists the folders could read in it what was asked and changed, which would end the cold review. The worktree holds only what git tracks, so an untracked history folder never reaches it; it is within reach only if git tracks it (`git ls-files -- <path>`), or with `--no-worktree`. In those two cases only, warn the user and ask, with AskUserQuestion (header "Session history"), before creating the worktree:
     - tracked: **Untrack it and add it to `.gitignore`** (Recommended): in the original repository, `git rm -r --cached -- <path>`, the path added to `.gitignore`, and a commit of these two changes only, so that the worktree is created without it; or **Keep it**, ignored by the agents only;
     - `--no-worktree`: **Use a worktree** (Recommended), or **Continue**, the folder ignored by the agents only.

     A session-history folder in git is almost always a mistake, and only a worktree keeps the folder physically out of the agents' reach; the agents' instructions forbid reading it in every case, but an instruction is a weaker barrier than an absent file. Changing the project's `.gitignore` or index is the user's decision, hence the question. Record the folders found and the answer in the register.
   - **Architecture tracked by git.** `SPECAUDIT_ARCH.md` must be in the worktree, where the audit and its agents read it. If `git ls-files` does not list it, or it has uncommitted changes, ask, with AskUserQuestion (header "Architecture"), before creating the worktree: **Commit it** (Recommended), alone, in the original repository (`git commit -m "spec-audit: project architecture" -- SPECAUDIT_ARCH.md`, with `git add` first for an untracked file); or **Use it for this audit only**: copy it into the worktree and record its SHA-256 in the register. Where no question can be asked, use it for this audit only, and say so. An audit never runs without it, so there is no option to ignore it.
   - **Configuration tracked by git.** The worktree holds only what git tracks, so an untracked or ignored configuration would not exist in it, and an audit run from an untracked configuration cannot be replayed or reviewed. If `.specaudit.md` or `.specaudit/` exists but `git ls-files` does not list it, or `git check-ignore` reports it ignored, warn the user and ask, with AskUserQuestion (header "Configuration"), before creating the worktree:
     - **Track it** (Recommended): `git add` it (with `-f` if a rule of `.gitignore` covers it, after saying which rule) and commit it alone in the original repository, so that the worktree is created with it;
     - **Use it for this audit only**: copy it into the worktree and record its SHA-256 in the register, as for an unversioned input;
     - **Ignore it**: audit without it.

     A configuration with uncommitted changes is handled like the document: audit the committed version, or commit first. Record the configuration used (path, commit or SHA-256) in the register.
   - **Reserve the audit's name** before creating anything: take the launch time of the command in local time, `<stamp>` = `YYYYmmdd_HHmmss`, and run `mkdir "<original repository>/SpecAudit-<stamp>"`, and on failure `-2`, `-3`… appended to the stamp: `mkdir` either creates the folder or fails, so two audits launched in the same second cannot get the same name. The name obtained, `SpecAudit-<stamp>`, is the audit's identifier: its results folder, its index entry, its attestation tag and its branch carry it. Step 5 records it.
   - Name the branch `audit/<stamp>`, with the stamp reserved above (`audit/20261013_102233`, or `audit/20261013_102233-2`): no other audit can have it, so it needs no suffix of its own. Name the directory `<parent of the repository root>/<repository name>-audit-<slug>`, with a suffix `-2`, `-3`… if it already exists outside `--resume` (two audits of the same document side by side).
   - Create it: `git worktree add "<directory>" -b audit/<stamp> <base>`, where `<base>` is `--base` or `HEAD`. With `--resume`, find it instead with `git worktree list`, by the branch the register records.
   - From now on, all commands run in the worktree (absolute paths, or `git -C "<directory>"`), and agents receive absolute paths in the worktree.
   - Files that git does not track (ignored caches, build outputs, PDF sources, environments) are not there: step 4 decides what the worktree takes from the original directory. Once the audit has started, nothing is read in the original directory any more.
   - With `--no-worktree`, work in place, on the current branch, which the user has isolated for the audit, but record `git status`: other sessions may be working in parallel, and their changes are not yours. The name is reserved the same way.
   - Outside a git repository, ask whether to initialize one: without git, there is neither isolation nor commits.
   - In all cases, commit only your files and never push.
4. **Environment.** The audit uses the worktree, the file tools, Bash, the two agents and the project's own oracles, nothing else. Establish that; step 5 records it in the register (format in `references/register.md`):
   - **Session inventory.** List what your session exposes and that the audit ignores: plugins and skills (`claude plugin list --json`, or the list in your context), connectors (`claude mcp list`), hooks. Record them as *ignored*. Never invoke a skill or a connector during the audit, in any mode: they bring context the reviewers must not have, and they are not reproducible.
   - **Oracles.** The oracle table is built from the architecture's `Oracles` table, not discovered: each row gives the oracle's path, kind, command, correspondence table and guard location. For each one, record its kind, its path, the statements or sections it covers (from its correspondence table, as the profile's `Oracles` section says), its command and its guard location, where the guards written for it go (`SKILL.md`, 4.2). An artifact of the worktree that looks like an oracle (a kind the profile's `Oracles` section lists) but is not in the architecture is not used: say so once, suggesting `/spec-audit:init` to add it, and record it in the register. Run each command once in the worktree, from its root: an oracle whose command does not run is not an oracle. Record the exact command you ran and saw pass, copied rather than rewritten (`pytest …` and `python3 -m pytest …` are not interchangeable: one may be installed as an executable without the module being importable), because the audit session receives only this table and an allow list built from it, and cannot try another form. Order the table by strength, as the profile does. This table goes to every reviewer (phase 1) and every adjudicator (4.1).
   - **Interpreter.** Find the interpreter that will run the agents' scripts, the corpus scripts and the protocol's scripts: run `python3 --version`, and keep `python3` only if it prints a Python 3 version; otherwise run `python --version` and keep `python` if it does. Exit status alone does not decide: on Windows, `python3` may be the Microsoft Store stub, which prints a message such as "Python was not found" (localized: "Python est introuvable") instead of a version. Record the one kept in the register (`Interpreter`); everywhere the protocol writes `<python>`, it means that command, and the audit never tries another one. If neither works, stop and ask, as below.
   - **Worktree autonomy.** `git -C "<original repository>" status --ignored --porcelain` lists what git ignores. For each ignored path an oracle needs, by nature:
     - *third-party cache* (`.lake/packages`, `node_modules`, a venv, a vendored dependency): **share** it from the original directory by a junction or symbolic link (`mklink /J` on Windows, `ln -s` elsewhere); it is read, not rebuilt, and the original is untouched;
     - *input the project does not version* (PDF sources, data files, `.env`): **copy** it once into the worktree and record its origin and SHA-256 in the register, so that the audit stays replayable and the report says what it ran on;
     - *build output of the project itself* (`.lake/build`, `target/`, `__pycache__`, `dist/`): **nothing**; the worktree rebuilds it from its own sources, which is what makes the baseline probative. A build output copied from the original directory could come from sources that differ from the commit audited.
   - **Stop and ask.** If an oracle cannot run from the worktree alone (toolchain missing, cache absent and too large to share, runner not installed), stop and ask the user, with AskUserQuestion, what to install or share. Never replace an oracle by a script of your own, and never start an audit whose baseline is not green from the worktree alone.
5. **Register.** Create `spec-audit/<slug>/register.md` (format in `references/register.md`), or reread it with `--resume`. It is the audit's memory: it must survive a context compaction, so update it after each step, not at the end. Record in it the launch time of the command in local time (`Launched`, `YYYYmmdd_HHmmss`, with the machine's UTC offset; a `--resume` keeps it), who launched it (`Launched by`, always filled, whatever the context, from the first source that answers: the `user.name` and `user.email` of git in the original repository, local then global, which is the identity its commits carry; else `GIT_AUTHOR_NAME` and `GIT_AUTHOR_EMAIL`; else the system user (`$USER`, `$USERNAME`, `id -un`); else `unknown`. Never a guessed identity. Write the source and the context after it, `(git, cloud session)`, `(system user, CI)`, so that a reader knows how far to trust it; a `--resume` by someone else adds a `Resumed by` line), which names the results folder at closing (8.4), this session, by its id as `SKILL.md` gives it ("Steps 1 to 6": the id written there, never the text `${CLAUDE_SESSION_ID}`, which this file, being read rather than loaded, does not fill in), and the state `running`: only the session that launched the audit may stop it (8.9), because only it knows the step in progress and the process or agents running.
   - Record the mode (`audit session`, with its process id and session id once launched at step 6, or `in-session`), the session inventory, the oracle table and the autonomy actions of step 4.
   - Name this session `[AUDIT] <slug>` if a tool lets you rename it (Claude desktop app); otherwise suggest once that the user run `/rename [AUDIT] <slug>`. The name tells the user which session to stop the audit from.
   - With `--resume`, before anything else of the resume: compare the options given with the register's (`SKILL.md`, "Options at resume"). A fixed option that differs stops the resume, with the option and the value recorded; a changeable one is recorded in the register (`Parameters` and its history) and applies from now on, the model flagged as such. The audit session is then launched with the register's values as they now stand, which are the `<options>` of its command.
   - With `--resume`: if the register's state is `running` or `stopping` and its session is not this one, the audit may still be running there. Decide from the process the register's `Mode` line records, never from the processes you can see: any `claude` process may be another session, or this one. If that process is gone (`kill -0 <pid>` fails), or `<worktree>-scratch/launch/ended` exists, the audit is not running: take over without asking. Only while it is alive, ask the user to confirm before taking over; without a question (non-interactive), stop and say which process is still running. Then record this session. The last commit of the audit branch is always a verified state (an internal revision, 4.3); the uncommitted changes after it were never verified. Save those to the document and the corpus, untracked files included, as `spec-audit/<slug>/in-flight-<YYYY-MM-DD>.patch`, restore the document and the corpus to the last commit, and redo the step in progress recorded in the register.
   - Also with `--resume`, before any other step of the audit, the orchestrator settles the agent table from the agents' journal (`SKILL.md`, "Agent journal"): an agent whose scratch directory holds its `result.md` is done, and is not launched again; since agents run one at a time, at most one is left without one, `running`, `stopped` or `pending`, and it is replaced (Roles, "Replacing an agent"), with its `prompt.md` as its message, word for word, on the revision at `HEAD`, and finds in its scratch directory the `partial.md` its predecessor wrote when a stop was requested, if any. Remove `stop-requested`, `pause-requested` and `agent-running` from the scratch root first, or the hooks would refuse the resumed audit too: no agent still works for this audit, and its scratch directory holds what it had done.
   - **Announce the audit in the index**, in the original repository, right after recording the launch time and the name reserved at step 3 (`Results folder` reserved, and the branch `audit/<stamp>`): add the audit's entry to `SPECAUDITS.md` at the root of the original repository, creating the file if it does not exist (format in `references/register.md`): a row at the top of the table, result `RUNNING`, and a section with the launch, the audited object, the base and a one-line paragraph saying the audit is running and where (worktree, branch `audit/<stamp>`). Write it with `index.py`, as `references/register.md`, "Writing the index", says, with the message `spec-audit(<slug>): launched`: another audit launched at the same moment writes its own entry in the same file, and only the script keeps both. The entry exists from the start because an audit whose session dies without warning (a crash, a reclaimed container) must still be visible, as `RUNNING`, rather than leave no trace. If the project rules forbid this commit, pass `--no-commit` and say so.
   - With `--resume`, keep the name and the entry: set its result back to `RUNNING`, with a line in its section saying when and by whom the audit was resumed.
6. **Audit session.** Unless `--in-session` is given, the audit runs in a session of its own, so that nothing of your session (plugins, skills, connectors, hooks, memory, conversation) reaches it, and so that what it may run is exactly the oracle table. From the worktree:
   - Write in `<worktree>-scratch/launch/`, the launch folder of this audit, regenerated at each launch and at each `--resume`, except its streams: first move an existing `stream.jsonl` to `stream-<n>.jsonl`, `<n>` the next free number (1, 2…), and keep every `stream-<n>.jsonl`, since each run's stream is the only record of what it consumed and the next run would overwrite it ("Consumption" below). Then write `protocol.md` with `<python> ${CLAUDE_SKILL_DIR}/references/protocol.py ${CLAUDE_SKILL_DIR} "<worktree>-scratch/launch" "<worktree>-scratch/protocol"`, adding `--fail-fast` when it is given and `--formal-oracle` when the oracle table has a formal oracle: it writes the skill's `SKILL.md`, the profile (`profiles/formal.md`) and `references/register.md`, without the sections only you or a rare case need (parameters, project configuration, closing, the index format, the results folder's manifest, the corpus error entry, and fail-fast or the Lean guard example when they do not apply), which go to `<worktree>-scratch/protocol/on-demand.md`, named in the prompt's last line. Never this file nor `references/closing.md`: the audit session needs neither. Every word of `protocol.md` is sent again with each of the orchestrator's turns, about sixty on the demo, so what it never reads costs as much as what it does; never write it by hand. Then copy `references/journal.py`, `references/arch.py`, `references/usage.py`, `references/report.md`, `references/corpus-errors.md`, `references/discharge.md`, `references/discharge.py` and `references/with_docs.py` into `<worktree>-scratch/protocol/`, where the audit session can read them when it needs them (it may not reach the plugin's folder), and add to `protocol.md` the line "The report template, the procedure for a suspect guard and hypothesis discharge are in `<worktree>-scratch/protocol/report.md`, `corpus-errors.md` and `discharge.md`, and its script in `discharge.py`: read each when SKILL.md says"; preceded by the line "You are the orchestrator of an audit prepared by its launcher: phase 0, steps 1 to 6, is done and recorded in the register; continue at step 7; launch no agent other than `spec-reviewer` and `spec-adjudicator`; never run phase 8, which the launcher does from your report"; and `agents.json`, the two agents of the plugin's `agents/` folder as the `--agents` format wants them (`description`, `prompt` = the body of the file, `tools`, `model`), under their names `spec-reviewer` and `spec-adjudicator`.
   - **Native paths.** Every path in the allow list, in the launch command and in the prompt, and every path the register gives the session (worktree, scratch root, corpus, documents), is in the form the session itself resolves. On Windows the audit session resolves Windows paths, not the MSYS paths of Git Bash: write `C:/Users/…/sa-audit-x`, never `/c/Users/…` nor `/tmp/…`, converting each with `cygpath -m "<path>"` (forward slashes, so that the rule needs no escaping), and record `paths: native` in the register. A rule written with an MSYS path matches no command the session runs, and every `<python> <scratch root>/…` is refused at the first preflight. Elsewhere, paths are already native.
   - Build the Bash allow list from the oracle table: `Bash(git *)` and, per oracle, its runner only (`Bash(python *)`, `Bash(pytest *)`, `Bash(lake *)`, `Bash(mvn *)`); and the interpreter of the register (`Interpreter`, written `<python>`: `python3`, or `python` where `python3` is a stub), restricted to two folders: the agents' scratch root, `<worktree>-scratch/` (`Bash(<python> <worktree>-scratch/*)`), for their own scripts, and the corpus (`Bash(<python> <worktree>/<corpus>/*)`), for the lint and any script the corpus runs outside its test runner. Nothing else: no network tool, no package installation, and `git push` denied. The interpreter rule is what lets an adjudicator execute an ad hoc counterexample, the only evidence when no oracle covers a statement; without it, every such error could only stay UNDECIDED, or be confirmed by you, which the protocol forbids. Restricting it to the scratch root keeps it to the agents' scripts.
   - Launch it in the background, from the worktree, and record its process id and `--session-id` in the register:

     ```text
     env <clean-env> CLAUDE_CONFIG_DIR="<folder chosen>" claude -p "Audit <document> <options>. Register: spec-audit/<slug>/register.md."
       --session-id <uuid> --model <family or id> --setting-sources "" --strict-mcp-config
       --tools "Read,Grep,Glob,Edit,Write,Bash,Agent"
       --disallowedTools Skill "Bash(git push *)"
       --agents "<worktree>-scratch/launch/agents.json" --append-system-prompt-file "<worktree>-scratch/launch/protocol.md"
       --permission-mode dontAsk --allowedTools Read Grep Glob Edit Write Agent "Bash(git *)" <one rule per oracle> <the two interpreter rules>
       --settings "<worktree>-scratch/launch/settings.json"
       --output-format stream-json --verbose > "<worktree>-scratch/launch/stream.jsonl"
     ```

     `settings.json`, written in the launch folder with `protocol.md`, registers the agents' journal (`SKILL.md`, "Agent journal") and the architecture's hook: `{"hooks": {"PreToolUse": [{"matcher": "Agent|Task", "hooks": [H]}, {"matcher": "Read|Edit|Write|NotebookEdit|MultiEdit|Grep|Glob", "hooks": [K]}], "PostToolUse": [{"matcher": "*", "hooks": [H]}], "PostToolUseFailure": [{"matcher": "Agent|Task", "hooks": [H]}], "SubagentStop": [{"hooks": [H]}], "SessionEnd": [{"hooks": [H]}]}}`, where `H` is `{"type": "command", "command": "<python> \"<worktree>-scratch/protocol/journal.py\" --stream \"<worktree>-scratch/launch/stream.jsonl\" --pause-at <value of --pause-at> --flag \"<scratch root>/pause-requested\" --ended \"<worktree>-scratch/launch/ended\" --stop \"<scratch root>/stop-requested\" --lock \"<scratch root>/agent-running\""}`. `K` is `{"type": "command", "command": "<python> \"<worktree>-scratch/protocol/arch.py\" hook --root \"<worktree>\" --corpus \"<corpus>\""}`: it refuses an Edit or a Write in the worktree outside what the architecture lets the audit change, any write of an agent in the worktree, and an agent's read of the index, the results folders, `spec-audit/`, the configuration, session history and the paths marked `original`, `prior-version` or `ignored` (`references/arch.py`); the refusal reaches the caller as the tool's error, which the orchestrator records (`SKILL.md`, "Standing rules", Architecture). `--setting-sources ""` loads no settings of yours, but `--settings` adds this file: hooks run outside the allow list, and this one writes only in the agents' scratch directories, the pause request, the lock and the end marker. It also holds the usage threshold: before each agent's launch it reads the session's own stream, and past `--pause-at` it writes the pause request and refuses the launch, so that the pause does not depend on the orchestrator remembering to check. And it holds the audit to one agent at a time (`SKILL.md`, "One agent at a time"): it makes every launch a foreground one, and refuses a launch while the previous agent has not returned.

     The stream carries, with every request, the account's usage of its two windows ("Usage limits" below).

     The launch files are in this audit's own folder, never in the scratchpad your session may be offered: that one is shared by every audit launched from the same session, and two audits launched side by side would overwrite each other's `protocol.md` and `agents.json`. Every tool the session uses is in `--allowedTools`, `Agent` and `Read` included: under `dontAsk`, a tool that is not allowed is refused, and a session that cannot launch its agents can confirm nothing. The prompt comes first, right after `-p`: `--allowedTools` and `--disallowedTools` take every argument that follows them, so a prompt placed after them is read as one more rule and the session starts without it.

     `--setting-sources ""` loads no settings file, hence no plugin, no hook and no connector of yours, and no default model either, which is why `--model` is always given (from the skill's `--model` and `--model-version`, otherwise the family of your session's model, latest version); `--strict-mcp-config` admits no MCP server; `--tools` names the built-in tools, `--disallowedTools Skill` removes the skills, and `dontAsk` denies anything that would prompt, so the allow list is the whole of what the session may run. The CLI's `--bare` mode is not used: it only accepts an API key and refuses the usual sign-in. The built-in agents (general-purpose, Explore, Plan) stay visible to that session; the protocol tells it to launch the two of `agents.json` only.
   - Wait for the process to end by its process id, recorded in the register: poll `kill -0 <pid>` every 30 seconds, in loops that stay within the Bash tool's time limit, and start a new loop until it fails. Never wait with `pgrep -f <pattern>`: the waiting command's own line contains the pattern, so it finds itself and never ends, which left a launcher waiting twenty minutes for a session that had already ended. Conversely, an empty output is not an end: `claude -p` writes its result only when it finishes, so its output file stays empty for the whole audit, and the register may not change for minutes while agents work. Only `kill -0 <pid>` failing says the session ended; until then, never relaunch, not even when it looks silent. A launcher that took a session running its preflight for one that "ended without output" launched a second one on the same register: the two overwrote each other's records, and the audit was counted as passing its preflight only at the third attempt. Write the process id and session id into the register's `Mode` line as soon as the launch command returns, before waiting.
